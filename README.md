# Расчёт форвардной кривой пшеницы

## Запуск после скачивания с GitHub

Нужен Python 3.12+. Команды для Windows PowerShell из папки проекта:

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip list
.venv/Scripts/python.exe -m pip install -r requirements.txt -r requirements-margin.txt
.venv/Scripts/python.exe run_project.py --example --serve
```

Ссылка на локальную страницу появится в терминале. Расчёт зерновой кривой работает по комплектному фиксированному набору. G-curve загружается с MOEX через HTTPS на дату набора, поэтому нужны сеть и доступность исторических данных MOEX. Для ГО нужен отдельный архив и портфель: в комплектном наборе их нет, и этот модуль явно сообщит об отсутствии данных. Остальные результаты сохранятся. Это исследовательский прототип, не готовая система реального клиринга.

Для полного запуска со своими данными заполни `input/` по [описанию формата](input/README.md), затем выполни `.venv/Scripts/python.exe run_project.py --serve`. Полная инструкция: [RUNNING_PROJECT.md](RUNNING_PROJECT.md). Исходный каталог нужен целиком: установка одного wheel не устанавливает CLI и комплектные входные файлы.

Проверка кода без сетевых запросов:

```powershell
.venv/Scripts/python.exe -m unittest discover -s tests -q
.venv/Scripts/python.exe -m pip check
```

## Сначала просто попробуй

Если окружение `.venv` уже подготовлено, повторно устанавливать зависимости не нужно.

Открой папку проекта и запусти **run.bat** двойным кликом. Программа сама возьмёт готовые массивы из examples/default_input.json. После завершения открой **output/comparison.png**: на нём предыдущая и новая кривые.

Сам исполняемый Python-файл называется **run.py**. Это входная точка проекта, не одиночный автономный скрипт: рядом с ним должны оставаться папки wheat_curve и examples. Если скачиваешь проект на другой компьютер, переноси всю папку или распаковывай ZIP целиком.

Для запуска из PowerShell:

~~~powershell
Set-Location -LiteralPath "путь/к/wheat-forward-curve"
.venv/Scripts/python.exe run.py
~~~

Не запускай .venv/Scripts/python.exe отдельно: это только интерпретатор. Ему нужно передать run.py, как в команде выше. Активация окружения не требуется.

Обычный запуск заканчивается сообщением с датой, количеством измеренных и перенесённых узлов, а также путём к результатам. Если окно после двойного клика закрылось, результаты остаются в output. Для чтения сообщений используй PowerShell.

## Что получится

| Файл в output | Что в нём |
|---|---|
| comparison.png | Предыдущая и новая кривые на одном графике |
| yesterday.png | Только предыдущая кривая |
| today.png | Только новая кривая |
| curve.json | Цены всех 39 узлов, источники, параметры и предупреждения |
| audit.json | Подробный расчёт: разложенные сделки, глубина и спред каждого среза, отсечение крайних цен |

Синие точки на новой кривой означают цену по сегодняшним данным. Оранжевые крестики означают перенос предыдущей цены, не новое измерение. Линии между узлами построены log-linear.

В готовом примере 39 предыдущих точек и 16 событий. Получаются 7 узлов по данным дня и 32 переноса. Это специально подготовленный пример, не реальные биржевые данные.

Повторный запуск в ту же выходную папку заменяет результаты. Для отдельного эксперимента укажи свою папку:

~~~powershell
.venv/Scripts/python.exe run.py --output output/my-experiment
~~~

## Маленький пример для ручной проверки

В examples/minimal_input.json оставлены одна предыдущая точка 4M, две заявки и одна отдельная сделка. У остальных сроков предыдущих цен нет.

~~~powershell
.venv/Scripts/python.exe run.py --input examples/minimal_input.json --output output/minimal
~~~

Покупка стоит по 20 500, продажа по 20 700 руб./т. На каждой стороне 100 т, заявки действуют весь день. Цена по заявкам равна 20 600. Отдельная сделка объёмом 200 т имеет цену 20 700. Она не связана с исполнением этих двух заявок.

Для 4M минимум сделок 200 т, полный вес 800 т. Поэтому вес сделок 200 / 800 = 0,25 и итог:

~~~text
0,25 × 20 700 + 0,75 × 20 600 = 20 625 руб./т
~~~

В output/minimal/curve.json цена 4M должна быть "20625.00", источник MIXED. Остальные 38 узлов будут NONE: данных для их расчёта или переноса нет. Количество нулей после запятой в JSON не определяет финансовую точность.

## Как подставить свои данные

Скопируй готовый пример, чтобы не потерять исходный:

~~~powershell
Copy-Item examples/default_input.json my_input.json
~~~

Открой my_input.json в текстовом редакторе. В нём есть четыре обязательные части:

| Поле | Что указать |
|---|---|
| calculation_date | Дата сегодняшнего расчёта, например "2026-10-15" |
| previous_date | Дата предыдущей кривой, например "2026-10-14" |
| previous_curve | Массив предыдущих цен по срокам |
| events | Массив сегодняшних событий заявок и сделок |

Даты нужны реальные для конкретного расчёта. Программа не подставляет текущую дату компьютера автоматически. После выходных previous_date может отстоять больше чем на один календарный день, но всегда должна быть раньше calculation_date.

После редактирования запусти:

~~~powershell
.venv/Scripts/python.exe run.py --input my_input.json --output output/my-data
~~~

### Предыдущая кривая

Каждая точка выглядит так:

~~~json
{"tenor": "4M", "price": "20500", "fallback_streak": 0}
~~~

tenor обозначает срок. Используются 1D, 1W, 2W и все месяцы от 1M до 36M. Это 39 точек, включая 12M, 24M и 36M. Не нужно добавлять дублирующие 1Y, 2Y, 3Y.

price это цена в рублях за тонну. fallback_streak показывает, сколько расчётных дней подряд цена переносилась; если её получили по данным предыдущего дня, укажи 0. Отсутствующее поле счётчика означает 0.

Цены и объёмы удобно записывать строками с десятичной точкой: "20500.50", "100.25". Запятая внутри числа не подходит. В Python передавай строки, int или Decimal, не float.

Если цены узла нет, его можно пропустить или указать price: null. Ноль не означает отсутствие цены и не принимается. Полностью пустой массив previous_curve не принимается.

Можно дополнительно передать maturity_date. Тогда она должна соответствовать сроку на previous_date. Также допускается точка только с maturity_date и price, если эта дата точно совпадает со стандартным узлом предыдущего дня. Произвольную нерегулярную сетку программа не пересчитывает автоматически.

Сроки постоянные, даты плавающие: вчерашний 4M служит справочной ценой сегодняшнего 4M, хотя дата его экспирации сдвинулась. На сравнительном графике каждая кривая расположена по собственным календарным датам.

### Сегодняшние события

Нужен журнал событий за один день, не просто стакан на закрытии. Без истории нельзя узнать, какие заявки стояли в течение дня.

Для каждого события обязательны event_id, event_type и time. Время московское, без часового пояса, от 10:00:00 до 18:00:00 включительно. Все события относятся к calculation_date. event_id уникален; trade_id у каждой сделки тоже уникален.

| event_type | Обязательные дополнительные поля | Что происходит |
|---|---|---|
| ORDER_NEW | order_id, side, price, quantity, maturity_date | Создаётся лимитная заявка |
| ORDER_MODIFY | order_id и хотя бы одно из price, quantity, maturity_date | Переданные поля активной заявки заменяются |
| ORDER_CANCEL | order_id | Заявка удаляется |
| ORDER_FILL | order_id, quantity | Объём исполнения вычитается из остатка |
| TRADE | trade_id, price, quantity, maturity_date, trade_type | Сделка участвует в расчёте дневной цены |

side принимает BUY для покупки и SELL для продажи. maturity_date означает дату экспирации контракта, не время отмены заявки. quantity всегда в тоннах; у ORDER_NEW это начальный остаток.

Пример создания заявки:

~~~json
{
  "event_id": "e1",
  "event_type": "ORDER_NEW",
  "time": "10:00:00",
  "order_id": "bid-1",
  "side": "BUY",
  "price": "20500",
  "quantity": "100",
  "maturity_date": "2027-02-15",
  "trade_type": "NON_ADDRESS"
}
~~~

Для новой заявки trade_type можно не передавать: по умолчанию это NON_ADDRESS. Адресные и рыночные заявки не поддерживаются.

Пример изменения остатка:

~~~json
{
  "event_id": "e2",
  "event_type": "ORDER_MODIFY",
  "time": "11:00:00",
  "order_id": "bid-1",
  "quantity": "150"
}
~~~

После такого изменения остаток станет 150 т. Это не добавление 150 т к старому остатку. Менять сторону заявки через ORDER_MODIFY нельзя.

Пример сделки:

~~~json
{
  "event_id": "e3",
  "event_type": "TRADE",
  "time": "11:30:00",
  "trade_id": "trade-1",
  "price": "20700",
  "quantity": "200",
  "maturity_date": "2027-02-15",
  "trade_type": "NON_ADDRESS"
}
~~~

В цену включаются только сделки NON_ADDRESS. Структурно корректная сделка ADDRESS исключается с предупреждением ADDRESS_TRADE_EXCLUDED в curve.json. Это не отменяет реальные события исполнения заявок.

**TRADE не уменьшает заявки автоматически.** Если сделка исполнила стоявшую заявку, отдельно передай ORDER_FILL с её order_id и исполненным количеством. Ссылки buy_order_id и sell_order_id у сделки допустимы, но сами по себе остатки не меняют. Для обеих исполненных сторон нужны соответствующие события исполнения.

На начало дня стакан пустой. Все уже стоящие к открытию заявки передай как ORDER_NEW на 10:00:00 с актуальными остатками. ORDER_NEW должен иметь новый order_id в пределах дня. Полное исполнение удаляет заявку; исполнение сверх остатка запрещено.

Для расчёта только по сделкам передай только TRADE. Для проверки чистого переноса передай events: [].

## Какие параметры используются

Параметры применяются к каждому узлу отдельно, а не к сумме объёмов группы сроков.

| Срок | Минимум сделок, т | Глубина каждой стороны, т | Объём полного веса сделок, т | Максимальный спред |
|---|---:|---:|---:|---:|
| 1D, 1W, 2W, 1M–3M | 800 | 100 | 1600 | 0,8% |
| 4M–6M | 200 | 100 | 800 | 1,2% |
| 7M–12M | 80 | 80 | 400 | 1,6% |
| 13M–24M | 80 | 80 | 400 | 2% |
| 25M–36M | 50 | 100 | 250 | 3% |

Минимум сделок определяет, хватает ли дневного объёма узла для цены по сделкам. Глубина определяет, до какого накопленного объёма смотреть цены отдельно на покупке и на продаже. Объём полного веса определяет влияние сделок при смешивании с ценой заявок.

Это выбранные рабочие настройки, не статистически доказанный оптимум рынка.

Для отдельного узла параметры можно заменить. Добавь в верхний уровень входного JSON поле parameter_overrides:

~~~json
"parameter_overrides": {
  "4M": {
    "min_trade_volume": "200",
    "min_order_volume": "100",
    "threshold_trade_volume": "800",
    "spread_max": "0.012"
  }
}
~~~

Можно указать только изменяемые поля, остальные останутся стандартными. spread_max задаётся долей: 0.012 означает 1,2%, а не 0,012%. Пороговые сравнения включают границы: объёма ровно на минимуме достаточно, спред ровно на максимуме допустим.

Общие настройки: окно 10:00–18:00, 160 срезов с шагом 3 минуты от 10:03 до 18:00, минимум 20 допустимых срезов на узел, отсечение по 10% цен с каждого края при числе срезов больше 20. Перенос допускается сколько угодно дней. Дополнительного требования к длительности жизни стакана нет.

## Что программа делает по шагам

### Шаг 1. Проверяет вход

Проверяются поля, даты, положительность цен и объёмов, уникальность идентификаторов и корректность истории заявок. Срок наблюдения должен быть от следующего календарного дня до 36 месяцев от calculation_date.

Неизвестная отмена, дубликаты, исполнение сверх остатка или пересечённый исходный стакан одной экспирации останавливают расчёт. Разные экспирации при проверке исходного пересечения между собой не сравниваются.

Все данные должны относиться к одному товару, качеству, валюте и ценовому базису. Программа не конвертирует лоты в тонны, валюты и условия поставки.

### Шаг 2. Определяет даты узлов

От сегодняшней даты отсчитываются 1 день, 7 дней, 14 дней и каждый календарный месяц до 36-го. Если соответствующего числа в месяце нет, используется последний день месяца. Выходные и праздники не сдвигаются.

### Шаг 3. Восстанавливает стакан и делает срезы

События сортируются по времени. При совпадении времени сохраняется порядок во входном массиве. Для каждого из 160 срезов определяется список активных заявок и их остатков.

Срез в 10:03 включает события с временем до 10:03:00 включительно. Аналогично последнему срезу предшествуют события ровно в 18:00:00. Срез это состояние в конкретный момент, не средняя за предшествующие три минуты.

### Шаг 4. Относит сделки и заявки к нужным узлам

Если дата экспирации наблюдения точно совпала с датой узла, цена и объём целиком относятся к нему.

Если дата лежит между двумя узлами, используется EMMI. Пусть T это дата наблюдения, TL и TR это соседние даты, P и Q это исходные цена и объём. RefL и RefR это предыдущие цены соответствующих сроков. Разности дат считаются в календарных днях:

~~~text
wL = (TR - T) / (TR - TL)
wR = (T - TL) / (TR - TL)

QL = Q × wL
QR = Q × wR

RefT = wL × RefL + wR × RefR
delta = P - RefT

PL = RefL + delta
PR = RefR + delta
~~~

Получаются два наблюдения: объём QL по цене PL на левом узле и QR по цене PR на правом. Общий объём сохраняется, сторона заявки не меняется. Предыдущая кривая фиксирована на весь день.

Если для разложения не хватает одной из справочных цен или получилась неположительная цена, расчёт останавливается с объяснением. Для точного попадания в узел справочная цена не нужна.

### Шаг 5. Считает дневную цену по сделкам

Для каждого узла складываются объёмы сделок после EMMI. Если их сумма меньше минимума, цены по сделкам нет. Иначе вычисляется VWAP:

~~~text
Ptrade = сумма(цена × объём) / сумма(объём)
~~~

Нужный минимум относится к объёму, попавшему именно в этот узел, а не к полному объёму исходной сделки. Отдельного требования к количеству сделок нет.

### Шаг 6. Считает дневную цену по заявкам

В каждом срезе покупки узла сортируются от дорогих к дешёвым, продажи от дешёвых к дорогим. На каждой стороне объём накапливается до требуемой глубины. Цена заявки, на которой этот объём впервые достигнут, и есть глубинная цена стороны.

Например, есть продажи 40 т по 20 600 и 80 т по 20 700. При глубине 100 т берётся 20 700, не средняя цена покупки 100 т.

~~~text
Mid = (глубинная цена продажи + глубинная цена покупки) / 2
Spread = (глубинная цена продажи - глубинная цена покупки) / Mid
~~~

Если на обеих сторонах достаточно объёма и спред не превышает максимум, срез даёт цену Mid. Иначе он пропускается.

При числе допустимых срезов меньше 20 дневной цены по заявкам нет. При ровно 20 усредняются все цены. При большем числе цены сортируются, отбрасывается целая часть N / 10 с каждого края, усредняются оставшиеся. При N = 21 это две цены снизу и две сверху.

20 срезов не обязаны идти подряд. Реальная длительность существования стакана между ними отдельно не проверяется.

### Шаг 7. Объединяет две дневные цены

Когда есть обе цены:

~~~text
w = min(объём сделок / объём полного веса, 1)
Итог = w × Ptrade + (1 - w) × Porder
~~~

Если есть только цена сделок, берётся она с весом 100%. Если есть только цена заявок, берётся она. Если нет обеих, переносится предыдущая цена того же срока без поправки. Если переносить нечего, получается NONE, а не ноль.

Перенос не ограничен количеством дней. Счётчик fallback_streak показывает его возраст и сбрасывается при появлении цены по сегодняшним данным. Сохранилось информационное предупреждение METHODOLOGY_REVIEW_REQUIRED при двух и более переносах: оно не запрещает расчёт и не означает автоматическую замену методики.

### Шаг 8. Строит кривую между узлами

Итоговая интерполяция log-linear: линейно меняется натуральный логарифм цены.

~~~text
u = (T - TL) / (TR - TL)
F(T) = exp((1 - u) × ln(F_L) + u × ln(F_R))
~~~

Здесь F_L и F_R это сегодняшние цены соседних узлов, u это положение даты между ними. Например, посередине между ценами 100 и 121 получится 110.

Это отдельная операция: в EMMI справочная линия остаётся арифметической, с абсолютным delta. На графиках линия рассчитана по дневной сетке этой log-linear интерполяции.

Пропуски не соединяются, отсутствующие узлы не дорисовываются. За пределами 1D–36M экстраполяции нет. Внутри расчёта используется Decimal с точностью 28 значащих цифр; до тика или целой тонны промежуточные результаты не округляются. В JSON цены сохраняются без дополнительного публикационного округления.

## Как посчитать следующий день

Возьми массив curve из полученного curve.json. Он становится previous_curve следующего расчёта без изменения структуры. Дата предыдущего расчёта становится previous_date. Поставь новую calculation_date и новый массив events. Вчерашние события повторно использовать нельзя.

Первую кривую нужно задать извне. Программа не создаёт её из рыночных данных автоматически.

Пример вызова из своего Python-кода в папке проекта:

~~~python
import json
from decimal import Decimal
from pathlib import Path

from wheat_curve import calculate
from run import encode

data = json.loads(
    Path("examples/default_input.json").read_text(encoding="utf-8"),
    parse_float=Decimal,
)
result = calculate(**data)

next_result = calculate(
    previous_curve=result["curve"],
    events=[],
    previous_date=data["calculation_date"],
    calculation_date="2026-10-16",
)

Path("next_result.json").write_text(
    json.dumps(next_result, ensure_ascii=False, indent=2, default=encode),
    encoding="utf-8",
)
~~~

В этом примере новый день без событий, поэтому все доступные цены переносятся. calculate возвращает Decimal; encode из run.py преобразует числа в строки для сохранения JSON. Функция сама не пишет файлы и не рисует графики.

Если параметры менялись через parameter_overrides, передай их и в следующий вызов. Старые параметры из result автоматически не применяются. Для полного воспроизведения сохраняй входной JSON вместе с результатом: audit содержит только расчётный вклад учтённых событий, не исходный журнал целиком.

Для подключения ядра к другому Python-проекту можно установить пакет из этой папки:

~~~powershell
python -m pip install .
~~~

После установки доступно from wheat_curve import calculate. Ядро не требует Pillow. Не запускай разовую установку для обычной пробы на этом компьютере: тут всё уже готово.

## Если что-то не получилось

| Ситуация | Что проверить |
|---|---|
| Не найден .venv/Scripts/python.exe | На этом компьютере открыта ли правильная папка; на другом нужно создать окружение |
| Не найден PIL | Для PNG нужен Pillow; можно считать без картинок с флагом --no-images |
| Ошибка чтения JSON | Кавычки, запятые между полями, формат дат, десятичная точка |
| REFERENCE_NODE_MISSING | Для даты между узлами должны быть обе предыдущие справочные цены |
| Не найдена заявка | Есть ли ORDER_NEW до MODIFY, CANCEL или FILL и правильный ли order_id |
| Почти всё перенесено | Проходят ли сделки и срезы по объёму, глубине, спреду и числу срезов; смотри audit.json |
| Узел NONE | Нет ни допустимой сегодняшней цены, ни предыдущей цены этого срока |
| На графике появились крестики | Это перенесённые цены, не ошибка изображения |

При некорректном входе программа завершится с кодом 2 и не сохранит новый результат. Старые файлы выбранной папки могут оставаться от прошлого успешного запуска. При сбое рисования JSON уже может быть сохранён, но код завершения будет ненулевым. Поэтому проверяй завершение команды и используй отдельные выходные папки для экспериментов.

Вход проверяется строго: адресные заявки, события вне окна, неверные поля и неправильные жизненные циклы не пропускаются молча. Исключение для структурно корректных адресных сделок описано выше: они исключаются с предупреждением.

## Установка на другом компьютере

Нужен Python 3.12 или новее. Распакуй весь проект, открой PowerShell в его папке и выполни:

~~~powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip list
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe run.py
~~~

В requirements.txt одна зависимость, Pillow 12.3.0, только для PNG. Для расчёта без картинок не нужно устанавливать никакие пакеты:

~~~powershell
python run.py --no-images
~~~

Папка .venv не переносится в ZIP: на другом компьютере её создают заново. Для кириллицы в изображениях используется системный Arial на Windows/macOS или DejaVu Sans на Linux.

## Как проверить программу

~~~powershell
.venv/Scripts/python.exe -m unittest discover -s tests -v
.venv/Scripts/python.exe -m pip check
~~~

Тесты проверяют расчёт, входные ошибки, пороги, 160 срезов, исключение адресных сделок, неограниченный перенос, EMMI, log-linear интерполяцию и запуск с сохранением PNG.

## Что важно перед реальным использованием

Этот проект делает расчёт по предоставленному журналу, но не подключается к бирже и не проверяет полноту биржевого потока. Пропущенная отмена или исполнение искажают восстановленный стакан.

Начальную кривую, полноту данных, единицы объёма, ценовой базис и публикационное округление должна обеспечить подключающая система. Автоматических экспертных поправок, фильтра выбросов, ограничения концентрации участников и сглаживания между днями здесь нет.

Исходное веб-приложение находится отдельно и этим обновлением не изменялось. Старые методические файлы и ZIP версии 1.0 отражают прежний снимок; действующие правила версии 1.1 описаны в этом README.
