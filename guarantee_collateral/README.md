# ГО портфеля зерновых форвардов

Модуль считает R, которое в нашем проекте называется ГО. Он переоценивает весь портфель в одинаковых сценариях зерновой и процентной кривых. Это модель проекта на основе предоставленной адаптации wheat_margin.py, а не официальный Единый лимит НКЦ и не сумма довнесения обеспечения.

Фронта нет. Расчёт работает из Python и командной строки. Архив не скачивается автоматически, отсутствующие дни и узлы не заполняются.

## Быстрая проверка

Команды выполняются из папки wheat-curve-calculator. NumPy/SciPy уже установлены в её .venv на этом компьютере.

```powershell
.venv/Scripts/python.exe -m tests.create_margin_test_input --output output/synthetic_margin_test_input.json
.venv/Scripts/python.exe run_portfolio_margin_calculation.py --input output/synthetic_margin_test_input.json --calendar examples/moex_spfi_trading_calendar_2026.json --allow-synthetic-test-data --output output/synthetic_portfolio_margin.json
```

Первая команда создаёт только технический тестовый пример: 201 синтетический снимок, 39 зерновых цен и 39 процентных факторов на каждую дату, покупка 1000 т и встречная продажа 400 т. Seed фиксирован. Это не согласованная рыночная модель генератора и не реальный архив. Вход и выход помечены SYNTHETIC_TEST; без явного разрешающего флага такой вход отклоняется.

Вторая команда действительно оценивает 78 моделей GARCH, генерирует 10 000 FHS-сценариев и использует исторические сценарии. Ни коэффициенты GARCH, ни ГО в примере не подставлены готовыми числами. Результат включает общий портфель и каждую сделку отдельно.

Пример не является рекомендацией по уровню ГО. Для рабочего расчёта нужен реальный архив и data_kind = REAL. Поле REAL является заявлением поставщика данных, а не независимой проверкой достоверности программой.

## Входной JSON

Это отдельный вход ГО, не журнал заявок и сделок за один день. Журнал сначала превращается зерновой считалкой в ежедневную кривую, а результаты накапливаются в архив.

| Поле верхнего уровня | Содержание |
|---|---|
| calculation_date | Дата оценки YYYY-MM-DD, совпадает с последней датой history |
| data_kind | REAL для рабочего архива или SYNTHETIC_TEST только для проверки |
| history_source | Непустое описание происхождения архива |
| history | Массив ежедневных снимков в возрастающем порядке |
| trades | Непустой массив оцениваемых форвардных позиций с уникальными trade_id |

Принцип структуры, не полный рабочий архив:

```json
{
  "calculation_date": "2026-10-16",
  "data_kind": "REAL",
  "history_source": "Описание фактического источника и базиса зерновых цен",
  "history": [
    {
      "date": "2026-01-05",
      "forward_curve": [
        {"tenor": "1D", "price": "20000", "source": "TRADES_ONLY"}
      ],
      "discount_factors": {"1D": "0.9996"}
    }
  ],
  "trades": [
    {
      "trade_id": "buy-1",
      "quantity": "1000",
      "strike": "21000",
      "side": 1,
      "fixing_date": "2027-04-14",
      "payment_date": "2027-04-16"
    }
  ]
}
```

Для настоящего запуска вместо показанной одной точки требуются все 39 узлов в каждой строке истории и минимум 201 последовательная торговая дата при стандартных параметрах. Короткий фрагмент выше намеренно не проходит проверки.

### Ежедневный снимок

forward_curve содержит ровно 39 точек: 1D, 1W, 2W, 1M…36M, без повторов и отсутствующих цен. Можно непосредственно взять массив curve из результата зерновой считалки. Порядок точек во входе произвольный; внутри они сопоставляются по tenor.

Для каждой точки обязательны tenor, положительная price и source. Допустимые источники: MIXED, TRADES_ONLY, ORDERS_ONLY, FALLBACK_PREVIOUS_DAY, EXPERT и SYNTHETIC_TEST. Последний недопустим при data_kind = REAL. Дополнительные диагностические поля результата зерновой считалки допускаются. Если передано maturity_date, оно должно совпадать с календарной экспирацией узла на дату снимка.

Перенесённые цены сохраняются с source = FALLBACK_PREVIOUS_DAY, используются в изменениях как есть и не обозначаются новым измерением. Отдельный счётчик таких наблюдений возвращается в результате. Экспертные цены явно помечаются EXPERT.

discount_factors является объектом из тех же 39 ключей. Его значения являются положительными конечными D на календарные экспирации соответствующих узлов данного дня. Это не ставки в процентах. Их можно получить от адаптера MOEX G-curve или другого совместимого источника. Для перевода возвращённого адаптером словаря date -> D в tenor -> D используется standard_nodes(дата снимка); нельзя перенести вчерашние даты как сегодняшние без явного расчёта.

Для каждого снимка вычисляются непрерывные нулевые ставки:

```text
tau_d,k = (календарная дата узла k на день d − d).days / 365
y_d,k = −ln(D_d,k) / tau_d,k
```

Все 39 сроков строго положительны, поэтому деления на нулевой tau нет. При необходимости отдельный источник ставок может сформировать эти D заранее. История цены не заменяет историю ставки.

Цены и объёмы в руб./т и тоннах, ставки внутри в долях единицы, D безразмерен. В JSON финансовые числа рекомендуется писать десятичными строками. Float/bool в публичных финансовых Python-структурах запрещены. Истории должны быть синхронными, без пропусков торговых дней и без нечисловых значений.

### Оцениваемые сделки

| Поле | Значение |
|---|---|
| trade_id | Уникальная непустая строка |
| quantity | Положительный объём в тоннах |
| strike | Положительная контрактная цена K в руб./т |
| side | Целое +1 для покупателя, −1 для продавца |
| fixing_date | Дата определения расчётного индекса |
| payment_date | Дата выплаты, не раньше fixing_date |

Это позиции для оценки, не сегодняшние биржевые записи TRADE. Одна исходная запись торговли может создавать позицию, но формат событий и формат оцениваемого контракта имеют разное назначение.

Текущее согласованное ограничение ГО: fixing_date строго позже конца горизонта риска. Фиксация ровно в дату конца горизонта, внутри горизонта или уже прошедшая отклоняется. Если неподдерживаемая сделка есть в портфеле, отклоняется весь расчёт; она не пропускается молча. Обе даты должны покрываться соответствующими кривыми 1D…36M. Различные даты фиксации/выплаты поддерживаются.

Поддержка фактических фиксингов уже зафиксированных сделок, денежных потоков внутри горизонта и их реинвестирования не включена: в конце обсуждения пользователь отложил это расширение.

## Календарь MOEX

Календарь передаётся отдельным файлом. Формат: market = MOEX SPFI; coverage_start и coverage_end; source_url; полный возрастающий массив trading_dates. Это снимок торговых дат, не список только тех дней, где случайно сохранилась кривая.

Дата конца горизонта равна h-му торговому дню строго после даты оценки. Сама дата оценки не считается первым днём. По умолчанию h = 5. Календарь обязан покрывать все даты архива и будущий конец горизонта. Пропуск торгового дня в архиве является ошибкой.

Пример examples/moex_spfi_trading_calendar_2026.json покрывает только 2026 год и основан на расписаниях MOEX https://www.moex.com/n96571 и https://www.moex.com/n94172, проверенных 27.10.2026. В нём 9 марта и 11 мая являются торговыми днями СПФИ, а 4 ноября не является. Дополнительные сессии выходного дня акций/срочного рынка не добавлены как самостоятельные дни СПФИ. За пределами покрытия программа не предполагает ни календарь понедельник–пятница, ни вечную неизменность праздничного расписания.

Например, для 30.10.2026 конец пятидневного горизонта 09.11.2026: 2, 3, 5, 6 и 9 ноября. Если архив начинается раньше 2026 года, необходимо передать более широкий проверенный календарь, а не пользоваться этим примером.

Для включения min_volatility_ratio необходимо передать previous_volatility. Настройки не определяются автоматически из вида текущей кривой. Заморозка по умолчанию отключена; Python API допускает передачу сохранённого объекта FHSCalibration через calibration. Для него проверяется неизменность исходной истории и сетки.

### Концентрация

Обе ставки по умолчанию нулевые, поэтому компонент равен нулю. Лимиты limit1/limit2 имеют null, корзины buckets пусты: они не утверждены и не выдумываются программой.

Чтобы включить компонент, пользователь должен явно установить ненулевые ставки, два лимита и корзины. Каждая корзина задаёт last_tenor, например 3M или 36M; пределы возрастают. Корзины имеют интервалы от предыдущей границы исключительно до своей включительно. Для первой корзины берутся сроки до её границы. Лимиты можно задать общими либо отдельно внутри корзины.

В каждой корзине X = abs(sum(side × quantity)). Надбавка равна:

```text
E2 = max(X − limit2, 0)
E1 = max(X − limit1, 0) − E2
A = E1 × addon1_per_tonne + E2 × addon2_per_tonne
```

Надбавки корзин складываются. Это выбранная зерновая адаптация в тоннах и руб./т, не официальный расчёт концентрационных объёмов валютных/процентных факторов НКЦ. Автоматической калибровки лимитов и ставок нет. Если включить ставки без лимитов/корзин, возвращается ошибка.

### Заданные стрессы

Каждый элемент hypothetical_scenarios или event_scenarios имеет name, forward_return и zero_shift. Первое изменение относительное, например −0.15 означает падение цены на 15%; второе абсолютное в долях, 0.02 означает +2 процентных пункта непрерывной ставки. Шок задаётся скаляром на всю кривую либо 39 значениями. Это интерфейс настройки, не рекомендуемые значения для реального рынка.

## Порядок расчёта

Изменения по архиву вычисляются по одинаковым tenor, без искусственного пересчёта истории на m/12 года:

```text
x_F(i,k) = F(i,k) / F(i−1,k) − 1
x_y(i,k) = y(i,k) − y(i−1,k)
```

По каждому из 78 факторов оценивается Student-t GARCH(1,1) без среднего ARMA:

```text
variance_i = omega + alpha × x_(i−1)^2 + beta × variance_(i−1)
e_i = x_i / sqrt(variance_i)
```

Начальная дисперсия и ограничения оптимизации сохранены из примера. Прогноз однодневной дисперсии использует последнее наблюдение; последующие дни условного прогноза omega + (alpha + beta) × предыдущая прогнозная дисперсия. Для нулевого ряда сохраняется исходная специальная ветка нулевой волатильности.

В каждом FHS-сценарии и каждом дне h выбирается одна историческая строка нормированных остатков одновременно для всех факторов. Так сохраняются их совместные исторические движения. Дневные относительные шоки зерновых цен перемножаются, абсолютные шоки нулевых ставок складываются. Отдельные случайные Student-t числа вместо исторических остатков не генерируются.

Исторический блок переносит фактически наблюдавшееся h-дневное относительное изменение цены и абсолютное изменение ставки на текущие узлы. Гипотетические и event-сценарии применяют явно заданные шоки.

В каждой текущей и сценарной оценке используется одна функция:

```text
V = side × quantity × D(d,payment_date) × (F_d(fixing_date) − strike)
```

Зерновые цены между соседними сегодняшними календарными узлами log-linear. Непрерывные нулевые ставки y между их узлами линейные, как в присланном модуле, D = exp(−y × фактические дни/365). Ставки, D и логарифмы D не следует путать: это разные варианты интерполяции. Параметрический адаптер MOEX сам вычисляет D без этой межузловой интерполяции; риск-модуль после шоков работает с переданной узловой историей y.

Дата оценки во всех сценариях остаётся сегодняшней. h определяет величину шока, не сдвигает дату, не сокращает сроки и не создаёт cash-flow переходы. Нет отдельного множителя sqrt(срок сделки).

Сценарные убытки L_n,j = V_0,j − V_n,j сначала складываются по сделкам в рамках каждого сценария. Только затем определяется портфельный риск. Сумма отдельных ГО не подменяет портфельное ГО.

Для VaR выбирается элемент ceil(confidence × N) возрастающего ряда убытков без интерполяции, результат ограничен снизу нулём. Для ES сохранено правило исходного примера с дробной долей граничного наблюдения верхнего хвоста. Для гипотетического и event-блоков используется худший неотрицательный убыток.

```text
ГО = R = max(R_FHS, R_Historical, R_Hypothetical) + A_Event + A_Concentration
```

Это согласованная формула зерновой адаптации при покрытой текущей переоценке и рублёвом денежном обеспечении. Она не является утверждением, что вся система Единого лимита НКЦ исчерпывается данной формулой.

## Python API и типы

```python
from datetime import date
from decimal import Decimal
from financial_contracts import ForwardTrade, NodeCurves, price_forward

trade = ForwardTrade("buy-1", Decimal("1000"), Decimal("21000"), 1,
                     date(2027, 4, 14), date(2027, 4, 16))
# curves = NodeCurves(дата оценки, 39 Decimal-цен, 39 Decimal-нулевых ставок)
# npv = price_forward(trade, curves)
```

Отдельный NPV не требует статистического архива или GARCH. Для него достаточно текущей NodeCurves и сделки с будущей фиксацией; ограничение по концу горизонта относится к ГО. price_forward также принимает discount_curve=совместимый_адаптер, например MoexGCurve с той же valuation_date. Тогда дисконт-фактор берётся непосредственно из выбранного адаптера, а не из линейной узловой ставки.

Для ГО доступны MarketHistory.from_records, TradingCalendar.load и calculate_portfolio_margin(market, trades, calendar, parameters_file=None). Для чтения целого входного словаря используется calculate_from_input. Тип ForwardTrade общий для текущей и сценарной переоценки. Историческая биржевая запись Trade из зернового event log не подменяет оцениваемый контракт: это другая сущность.

Цены, объёмы, дисконтирование, NPV, сценарные денежные оценки и концентрация рассчитываются в Decimal с точностью 28 значащих цифр, ROUND_HALF_EVEN. GARCH, сценарные шоки и статистическая оценка хвоста используют float64. На границе стоят явные преобразования; перевод float64 в Decimal не восстанавливает утраченную статистическую точность. Публикационного округления до копеек не введено.

## Результат и ошибки

portfolio содержит fhs, historical, hypothetical, event, concentration, go и current_value. trades содержит аналогичные результаты каждой позиции. Денежные значения в JSON являются десятичными строками в рублях.

Также сохраняются фактические параметры и их происхождение, дата оценки, конец горизонта, источник/тип истории и календаря, число исторических и FHS-сценариев, число переносов в истории, использованное окно и параметры GARCH. Полный массив остатков не заменяется этим кратким отчётом: для заморозки нужно сохранять именно объект калибровки. Для воспроизводимости сохранять исходный вход, календарь, параметры, версию кода и версии NumPy/SciPy.

Нельзя получить успешный результат при неподдерживаемой сделке, пропуске узла/дня, выходе за календарь или кривые, неверной единице, несходимости GARCH, неположительной сценарной цене или нечисловой оценке. Неположительные сценарные цены не обрезаются молча. Код завершения CLI 0 при успехе, 2 при ошибке. Старый выходной файл при ошибке входа/расчёта может остаться от прежнего запуска, поэтому проверять код завершения.

Калькулятор не проверяет экономическую корректность заявленного внешнего архива и не конвертирует качество зерна, базис, валюты и тонны автоматически. Пропущенные исходные исполнения/отмены нельзя исправить на стадии ГО.
