# Входные данные: зерновая кривая и ГО

Что передать программе, чтобы выполнить рабочий расчёт. Сначала зерновая кривая, затем ГО портфеля. Значения порогов и настройки модели описаны отдельно в [PARAMETERS.md](PARAMETERS.md).

Общий запуск: `.venv/Scripts/python.exe run_project.py --serve`. Файлы помещаются в `input/`. Даты записываются как `YYYY-MM-DD`, время как `HH:MM:SS` по Москве, без часового пояса. Цены в рублях за тонну, объёмы в тоннах. Десятичные числа удобно передавать строками с точкой: `"20500.50"`, `"100.25"`. При вызове Python API используются строки, int или Decimal, не float.

## 1. Данные для зерновой кривой

### 1.1. Дата расчёта

Дата выбирается в порядке: аргумент `--date`, поле `calculation_date` в `input/run_settings.json`, текущая дата Москвы. Файл настроек даты необязателен:

```json
{"calculation_date": "2026-10-30"}
```

Дата во входных блоках должна совпадать с выбранной датой расчёта. Предыдущая кривая относится к своей отдельной дате `previous_date`.

### 1.2. Файл `input/wheat_curve_input.json`

| Поле | Обязательность | Содержание |
|---|---|---|
| `calculation_date` | Да | Дата сегодняшнего расчёта |
| `previous_date` | Да | Дата предыдущей кривой, строго раньше даты расчёта |
| `previous_curve` | Да | Непустой массив предыдущих узловых цен |
| `events` | Да | Массив сегодняшних событий заявок и сделок; пустой массив допустим |
| `data_kind` | Для ГО обязательно | `REAL` для рабочих данных. Это заявление поставщика, не проверка достоверности программой |
| `source_description` | Нет | Пояснение происхождения данных |
| `parameter_overrides` | Нет | Переопределение четырёх порогов отдельных узлов; состав полей в [справочнике параметров](PARAMETERS.md#11-настраиваемые-пороги) |

Сетка состоит из 39 сроков: `1D`, `1W`, `2W`, все месяцы `1M`...`36M`. `12M`, `24M`, `36M` не нужно дублировать обозначениями `1Y`, `2Y`, `3Y`.

### 1.3. Точки `previous_curve`

| Поле точки | Обязательность | Содержание |
|---|---|---|
| `tenor` | Да, либо вместо него точная `maturity_date` | Обозначение узла, например `4M` |
| `price` | Да | Положительная предыдущая цена; `null` означает отсутствие цены, не ноль |
| `fallback_streak` | Нет | Неотрицательное целое: сколько расчётных дней подряд переносилась цена; по умолчанию `0` |
| `maturity_date` | Нет при наличии `tenor` | Дата экспирации узла на `previous_date`. Если передана, соответствие проверяется |

Пример одной точки: `{"tenor": "4M", "price": "20500", "fallback_streak": 0}`.

Допускается передать массив `curve` из предыдущего результата: поля `source`, `trade_price`, `trade_volume`, `order_price`, `trade_weight`, `valid_snapshots` принимаются, но не заменяют справочную цену. Дублирующиеся сроки запрещены. Отсутствующий узел можно пропустить. Для EMMI требуются необходимые справочные цены соседних узлов; для последующего общего расчёта NPV и ГО сегодняшняя кривая должна получиться полной, из 39 положительных цен.

### 1.4. Журнал `events`

Нужна история изменений за день, а не один стакан на закрытии. Программа сама восстанавливает состояния заявок и строит срезы. Каждое событие содержит `event_id`, `event_type`, `time`. `event_id` непустой и уникальный, время в пределах 10:00:00...18:00:00 включительно.

| `event_type` | Обязательные дополнительные поля | Смысл |
|---|---|---|
| `ORDER_NEW` | `order_id`, `side`, `price`, `quantity`, `maturity_date` | Создать безадресную лимитную заявку. `side`: `BUY` или `SELL`. `quantity`: начальный доступный остаток |
| `ORDER_MODIFY` | `order_id` и хотя бы одно из `price`, `quantity`, `maturity_date` | Заменить указанные поля активной заявки. Новый объём заменяет остаток, не прибавляется к нему |
| `ORDER_CANCEL` | `order_id` | Отменить активную заявку |
| `ORDER_FILL` | `order_id`, `quantity` | Уменьшить остаток на исполненный объём |
| `TRADE` | `trade_id`, `price`, `quantity`, `maturity_date`, `trade_type` | Отдельная сделка для расчёта дневной цены |

У новой заявки и сделки цена и объём положительные. `maturity_date` означает экспирацию контракта, а не момент отмены заявки: она после даты расчёта и не позже узла `36M`. `order_id` связывает жизненный цикл заявки. `trade_id` уникален среди сделок дня.

В `ORDER_NEW` поле `trade_type` необязательно: по умолчанию `NON_ADDRESS`; другое значение не допускается. У `TRADE` поле обязательно: `NON_ADDRESS` включается в расчёт, структурно корректная `ADDRESS` исключается с предупреждением. У сделки также необязательны `buy_order_id`, `sell_order_id`, `side`. Поле `comment` необязательно для всех событий.

Изменение стороны заявки через `ORDER_MODIFY` не поддерживается: нужна новая заявка. Запись `TRADE` сама по себе не исполняет заявку; для изменения остатка нужен `ORDER_FILL`. События с одинаковым временем обрабатываются в порядке исходного массива.

### 1.5. Что обеспечивает поставщик данных

Журнал должен содержать необходимые выставления, изменения, отмены и исполнения. До изменения или удаления заявка уже должна существовать; исполнение не может превышать остаток. Пропущенные события программа не восстанавливает. Пересечение стакана исключается поставщиком как на исходных сроках, так и после переноса заявок EMMI на стандартные узлы.

## 2. Данные для ГО портфеля

### 2.1. Полный состав

| Данные | Откуда берутся | Для чего нужны |
|---|---|---|
| Сегодняшняя зерновая кривая, 39 узлов | Строится из данных раздела 1 | Текущая и сценарная оценка позиций |
| Сегодняшняя процентная кривая | Общий запуск загружает MOEX G-curve по HTTPS на дату расчёта | Дисконтирование и сегодняшний процентный снимок |
| Портфель `trades` | Пользовательский JSON | Договорные позиции, для которых считается ГО |
| Архив `history` | Пользовательский JSON | Оценка исторических изменений, GARCH и сценариев |
| Торговый календарь MOEX SPFI | Пользовательский JSON | Проверка полноты истории и вычисление конца горизонта риска |
| Параметры риска | Общий файл параметров | Горизонт, число сценариев, доверительный уровень и прочие настройки |

Договорные позиции `trades` не нужно смешивать с рыночными сделками `TRADE` из `events`. Первые оцениваются, вторые используются для построения зерновой кривой.

### 2.2. Файл `input/portfolio_margin_input.json`

| Поле | Обязательность для ГО | Содержание |
|---|---|---|
| `calculation_date` | Да | Дата расчёта, совпадающая с общим запуском |
| `data_kind` | Да | `REAL` для рабочего архива |
| `history_source` | Да | Непустое описание фактического источника истории |
| `history` | Да | Массив ежедневных снимков в возрастающем порядке дат |
| `trades` | Да | Непустой массив оцениваемых позиций с уникальными идентификаторами |

### 2.3. Каждая позиция в `trades`

| Поле | Формат и единицы | Ограничение |
|---|---|---|
| `trade_id` | Непустая строка | Уникален внутри портфеля |
| `quantity` | Положительное десятичное число, т | Например `"1000"` |
| `strike` | Положительная договорная цена, руб./т | Например `"21000"` |
| `side` | Целое число `1` или `-1` | Покупка или продажа; не `BUY`/`SELL` |
| `fixing_date` | `YYYY-MM-DD` | Строго после конца горизонта риска |
| `payment_date` | `YYYY-MM-DD` | Не раньше фиксации; в пределах процентной кривой |

Все шесть полей обязательны. Фиксация должна находиться в пределах зерновой кривой. Фиксации внутри горизонта, на его границе и уже зафиксированные позиции не поддерживаются; неподходящая позиция отклоняет весь портфель.

### 2.4. Каждый снимок `history`

| Поле | Содержание |
|---|---|
| `date` | Дата снимка; даты строго возрастают, без повторов |
| `forward_curve` | Ровно 39 точек с `tenor`, положительной `price` и `source` |
| `discount_factors` | Объект с теми же 39 ключами сроков; значения положительные дисконт-факторы D на фактические экспирации узлов этого дня |

Признаки `source`: `MIXED`, `TRADES_ONLY`, `ORDERS_ONLY`, `FALLBACK_PREVIOUS_DAY`, `EXPERT`. Это происхождение цены, а не параметр модели. Если в исторической точке передана `maturity_date`, она должна соответствовать сроку на дату снимка. Порядок точек произвольный: соответствие определяется по `tenor`. Пропуски цен и дисконт-факторов запрещены. D передаётся коэффициентом, например `"0.98"`, не процентной ставкой.

При текущем минимуме 200 изменений рабочий архив должен содержать не меньше **201 снимка**, включая дату расчёта. Для полного окна FHS нужны 1001 снимок. Это последовательные торговые даты календаря MOEX, а не все календарные дни. Сравниваются одинаковые обозначения сроков: `1M` с `1M`, `2M` с `2M` и так далее.

В общем запуске можно передать архив по предыдущий торговый день: сегодняшняя рассчитанная зерновая кривая и дисконт-факторы добавляются в рабочую копию. Поэтому до добавления сегодняшнего дня могут быть 200 снимков. Если сегодняшний снимок уже есть, он заменяется новым с записью в журнал. Будущие даты и пропуски торговых дней не допускаются. Исходный файл не изменяется.

### 2.5. Файл `input/moex_trading_calendar.json`

| Поле | Формат и значение |
|---|---|
| `market` | Строка `MOEX SPFI` |
| `coverage_start`, `coverage_end` | Начало и конец проверенного покрытия, `YYYY-MM-DD` |
| `trading_dates` | Возрастающий массив торговых дат без повторов |
| `source_url` | HTTPS-ссылка на источник календаря |

Календарь должен покрывать весь архив, дату расчёта и конец горизонта риска. При горизонте 5 нужны следующие 5 торговых дат после даты расчёта. Дополнительно допустимы информационные поля `verified_on`, `secondary_source_url`, `secondary_source`, `notes`.

### 2.6. Процентная кривая

В общем запуске G-curve не нужно класть в `input/`: загрузка по HTTPS выполняется на точную дату расчёта. Нужны сеть и доступность снимка MOEX за эту дату. Ошибка загрузки не подменяется вчерашней кривой. Исторические дисконт-факторы программа не скачивает вместо пользователя: они должны быть в архиве.

Отдельный модуль ГО без общего запуска читает уже готовый архив, заканчивающийся датой оценки, и не добавляет сегодняшние рыночные данные сам. Для отдельного NPV нужны позиции и текущие кривые; архив и торговый календарь ему не требуются.

## Общие правила файлового входа

В рабочем общем запуске отсутствующий блок ищется в одноимённом файле `default_input/`; происхождение явно записывается в результат. Даты выбранных блоков должны подходить к расчёту. Пустой массив, `null` или некорректный пользовательский файл не заменяются корректным примером. Для рабочего расчёта следует передать полный согласованный набор, а не полагаться на резервные демонстрационные блоки.
